Closed joint BE/FE contract v3.1 `a36e903`: GET `/products/:productId/editorial` and GET `/catalog-editorial/vocabulary`; POST `/products/:productId/editorial/draft/initialize` with `{expectedCycle}` returns 201; PUT `/products/:productId/editorial/draft` with `{expectedCycle,expectedRevision,document}` returns 200. Initialize `expectedCycle` is explicitly `number | null`: null only when GET cycle is null, otherwise the current positive cycle. Save `expectedCycle` must be a positive number (null is rejected); BE U1 f5a085a supplied this explicit request distinction. `expectedRevision` is the positive draft revision loaded by the editor. Initialize/save success bodies are the top-level `EditorialState` from S5 plus optional top-level `warnings` from S8: `{cycle,draft,published,warnings?}`. There is no `data`, `state` or receipt wrapper. Initialize-empty example: `{"cycle":1,"draft":{"revision":1,"basePublishedRevision":null,"document":{"commercialTitle":null,"description":null,"mediaRefs":[],"familyCode":null,"values":[]}},"published":null}`. The HTTP client returns AxiosResponse; the feature API should unwrap its `.data` consistently with existing feature APIs, without changing the shared interceptor. Writes require `Idempotency-Key` of 1–200 characters, not trimmed. All responses no-store. No HTTP create(document), publish, operational field copying or new media endpoints.
S4. Exact grants: `read:ProductEditorialDraft` for reads and both read plus `update:ProductEditorialDraft` for writes; wildcard/manage and Product CRUD do not substitute. Dedicated `/pos/products/:id/editorial` route after existing auth/tenant/permission hydration, with feature-local exact checks. Do not alter shared CASL. An optional operational Product entry cannot be the only entry. Editor must not be inside operational form/disabled fieldset. Risk: item 2 for access gates; item 3 if shared transport/router behavior changes.
S5. State: `{cycle:number|null,draft:{revision:number,basePublishedRevision:number|null,document}|null,published:{revision:number,document}|null}`. GET has no warnings and returns stored history, which may be malformed. Unreadable documents remain unreadable/read-only, never normalized to blanks. Initialize-empty yields all five document keys: `{commercialTitle:null,description:null,mediaRefs:[],familyCode:null,values:[]}`. Oversized valid history stays readable and intact.
S6. Document is closed with required `commercialTitle:string|null`, `description:string|null`, unique private-product `mediaRefs:string[]`, `familyCode:string|null`, `values`. Null family requires empty values. Values have required `code`, `owner:'product'|'sellable'`, `variantId:string|null`, discriminated `type` and `value`: text/string, boolean/boolean, number/finite number plus required `unit:string|null`, single/option code, multi/unique option codes. One `[code,variantId]` tuple; owner/type/code must match selected-family bindings. Product owner uses null; sellable owner depends on the complete qualified variant set, not the operational flag. Never derive variant inventory from saved assignments.
S7. Fresh-save limits only: title ≤200 and description ≤20,000 Unicode code points (outside-BMP counts as one), ≤20 media, ≤200 values. Do not truncate or reject GET/initialize/history because of these new limits. Serialized request body ≤100 kB UTF-8; framework errors may bypass the editorial envelope. Media references remain unchanged; no upload/list/read mocks, picker, thumbnails or fake URLs while media contract remains open.
S8. Baseline-based archived conservation: only the same persisted family/definition/owner/variant/type/option assignment may remain. BE clarification b491f036 (main c4a806f): identity compares familyCode/value.code/owner/variantId/type/optionCode against CURRENT vocabulary for candidate and persisted baseline, never historical IDs. A definition ID replacement alone does not reject conservation if current bindings/type/options/units still qualify; IDs map current bindings and warning payloads only. Missing codes/options invalidate fresh saving, not silent historical normalization. There is no historical ID metadata or additional HTTP field. No introducing, moving or re-adding archived assignments after persisted removal. Initialize preserves Published assignments under D16. Save/initialize may return `ARCHIVED_OPTION` warnings with familyId/definitionId/owner/variantId/optionCode; map via vocabulary IDs, not invented labels.
S9. Separate authoritative GET state, local editable buffer and immutable pending intent. New confirmed action gets a new key; ambiguous retransmission uses the identical key and body. Receipt/replay is historical acknowledgement, not current state. No autosave. 409 preserves buffer and offers explicit reload/reconciliation; equal GET revisions do not diagnose key misuse or authorize resend. Preserve buffer on failures; no operational query invalidation. Editorial controller/guard errors are `{statusCode,error}` with 400 MALFORMED,401 UNAUTHORIZED,403 FORBIDDEN,404 NOT_FOUND,409 CONFLICT,500 INTERNAL_ERROR; framework/unknown bodies get safe fallback without raw messages.
S10. Vocabulary: families `{id,code,label,bindings:[{definitionId,definitionCode,owner,sortOrder}]}` and definitions `{id,code,label,type}`; number requires units `[{code:string|null,label:string|null,sortOrder}]`, single/multi require options `[{code,label,archived,sortOrder}]`, text/boolean have neither. Empty binding/option arrays allowed. Order families by label/code, definitions by code, bindings/options/units by sortOrder/code with null unit first. Labels originate in BE; no FE label catalog. Auth-scoped query caches despite companywide vocabulary.

Complete list ordered by name then id; no pagination, truncation, hasVariants flag, SKU, stock or prices. Actual nonempty membership requires sellable variantId from the list; empty means null. Key by id; duplicate names may use short ids only as a visual aid. Snapshot is not tied to draft revision or final save authority. Preserve and mark orphaned saved values for explicit correction; no silent deletion. No Product CRUD requirement.
